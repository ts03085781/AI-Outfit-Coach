# AI 穿搭教練 MVP 設計規格

日期：2026-08-07

## 1. 產品目標

打造一個免登入的手機 PWA，協助對日常穿搭缺乏信心的使用者，在一分鐘內完成拍照並取得溫和、具體、可以立即採用的穿搭建議。

第一版的核心成功指標是：使用者認為建議具體，且願意照做。產品不以提高互動時間、導購或社群分享為主要目標。

## 2. 產品原則

- 先肯定可觀察到的優點，再提出改善方式。
- 優先調整現有穿搭，不製造購物壓力。
- 不以數字評分，不比較使用者，也不評論外貌或身材好壞。
- 建議最多三項；若穿搭已合適，不為了輸出內容而硬改。
- 照片只用於當次分析，不建立長期影像紀錄。
- 不確定時說明限制並要求重拍，不虛構照片細節。

## 3. 目標使用者與情境

主要使用者是對日常穿搭缺乏信心，希望快速得到明確建議的一般使用者。

MVP 提供四種情境：

1. 日常外出
2. 約會
3. 工作／面試
4. 正式活動

使用者可選填天氣、室內／戶外，以及想呈現的感覺。自由輸入僅作背景補充，不取代四個主要情境。

## 4. 核心流程

1. 使用者選擇一種情境，必要時填寫選填背景。
2. PWA 開啟相機或相簿，使用者提供一張完整穿搭照。
3. 前端檢查格式、檔案大小與基本影像品質，並在本機壓縮。
4. 上傳前顯示資料處理說明，使用者主動勾選同意。
5. 前端將照片與情境傳給後端協調 API。
6. 後端把請求交給多模態 AI，驗證結構化輸出及安全規則。
7. 前端依固定順序顯示結果，優先突出最值得採用的一項建議。
8. 使用者可進行一次簡短追問，例如要求不需新增單品的替代方法。
9. 使用者可匿名回覆建議是否有幫助。

## 5. 回饋格式

後端只接受以下兩個互斥分支之一的 AI 結果：

**正常分析（`retake_required: false`）**

- `summary`：一句中性、溫和的整體觀察。
- `strengths`：恰好兩個、能由照片支持的優點。
- `occasion_fit`：`適合`、`稍需調整` 或 `不太適合`。
- `suggestions`：零至三個可立即完成的調整。
- `suggestions[].action`：要做的具體動作。
- `suggestions[].reason`：建議依據。
- `suggestions[].expected_effect`：預期改善。
- `retake_reason`：必須為空值（`null`）。

**重拍（`retake_required: true`）**

- `retake_reason`：非空的具體重拍原因。
- 不得包含 `summary`、`strengths`、`occasion_fit` 或 `suggestions`。

兩個分支均不得含有未定義欄位；重拍分支停止分析，不產生穿搭評價或改善建議。

## 6. 安全邊界

照片可以包含臉部，但 AI 不得分析或推測：

- 長相、吸引力或身材好壞
- 性別、年齡、族群或其他敏感身分
- 健康、經濟狀況或人格

AI 不得使用羞辱、嘲笑、命令式語氣，不得建議極端節食、塑身或非必要購物。主觀審美必須表達為可選建議，不能宣稱為絕對規則。

涉及婚喪喜慶、宗教或文化禮俗時，只提供一般原則，並提醒使用者確認主辦方或場地要求。

## 7. 系統架構

### 7.1 手機 PWA

負責情境選擇、相機／相簿操作、本機影像壓縮、同意畫面、結果呈現、一次追問與匿名有用性回饋。前端不得持有 AI 供應商金鑰。

### 7.2 後端協調 API

採無狀態設計，負責請求驗證、限流、暫時持有影像位元、組合提示、呼叫 AI、驗證輸出結構、安全過濾及錯誤轉換。影像不得寫入檔案、物件儲存、資料庫、追蹤系統或日誌。

### 7.3 多模態 AI 介面

以單一供應商介面封裝圖片分析與結構化輸出，應用層不依賴特定模型名稱。初版整合支援圖片輸入與 JSON Schema 的多模態 API；模型名稱透過部署設定指定，以便在不改產品流程的情況下更新模型。

### 7.4 最小化遙測

只記錄匿名事件與技術指標：情境類型、是否分析成功、延遲、錯誤分類、是否重拍，以及建議是否有用。不得記錄照片、自由文字、AI 完整回覆、IP 位址或持久化裝置識別碼。

## 8. 資料生命週期與隱私

- 原始照片與壓縮照片只存在於瀏覽器及後端請求記憶體中。
- 後端請求成功、失敗或逾時後，都必須釋放影像資料。
- 照片、分析文字與追問內容都不寫入永久儲存。
- 供應商必須提供不以內容訓練模型的設定，並符合產品公開聲明中的實際保留期限。
- 若供應商仍有安全或濫用監控保存期，介面必須揭露真實期限，不得宣稱「完全立即刪除」。
- 日誌、錯誤追蹤及分析服務必須設定欄位白名單，避免意外收集請求本文。

## 9. 介面設計

流程分為四個單一任務畫面：

1. 選情境
2. 拍攝穿搭
3. 預覽與知情同意
4. 顯示分析結果

每頁只有一個主要操作。結果頁依序顯示整體觀察、兩個優點、場合適合度及最多三項建議；第一項建議在視覺上優先。結果不顯示總分、排行榜或他人比較。

離開或重新整理頁面後，不提供結果復原。介面應在分析前清楚提醒此限制。

## 10. 錯誤處理

- 照片太暗、模糊、衣物被遮住或人物不完整：停止評價，指出原因並引導重拍。
- AI 無法可靠辨識衣物：停止分析，不輸出推測結果。
- AI 逾時或服務失敗：清除影像資料，顯示可安全重試的訊息。
- 結構化輸出驗證失敗：後端自動重試一次；再次失敗則回傳一般錯誤。
- 不適當或不支援的圖片：停止分析，以中性文字說明此服務只處理穿搭照。
- 追問偏離穿搭範圍：簡短拒絕並把對話導回當次建議。

## 11. 測試策略

### 功能測試

- 四種情境、拍照、相簿上傳、同意、分析、重拍、追問及回饋流程。
- 格式、大小、逾時、供應商失敗與無效 JSON 的處理。

### 安全與公平測試

- 涵蓋不同膚色、體型、性別表現、服裝文化及輔具。
- 測試低光、逆光、不同角度、遮擋、多人及非穿搭照片。
- 對抗測試誘導 AI 評論外貌、推測敏感特徵或輸出羞辱內容。
- 相同服裝只改變使用者外觀特徵時，建議不應出現無關差異。

### 隱私測試

- 驗證成功、失敗、重試與逾時後皆無影像檔案或資料列殘留。
- 掃描應用日誌、錯誤追蹤與分析事件，確認沒有照片或完整內容。
- 驗證前端重新整理或離開後無法恢復分析資料。

### 產品驗證

結果頁詢問「這項建議有幫助嗎？」並以匿名肯定率作為核心指標。質化測試另詢問使用者是否理解建議，以及是否願意立即採用第一項調整。

## 12. MVP 範圍外

- 帳號、跨裝置同步及歷史紀錄
- 個人數位衣櫃
- 即時連續攝影分析
- 商品推薦、聯盟導購及購物連結
- 社群、分享、排行榜及他人評分
- 自建電腦視覺模型或獨立穿搭規則引擎
- 數字分數、外貌評分與身材評價

## 13. 驗收標準

- 新使用者可在手機瀏覽器內，免登入完成一次分析。
- 四種情境皆能得到固定格式的結果或清楚的重拍原因。
- 正常結果包含兩個具體優點及不超過三項建議。
- 建議優先使用現有穿搭調整，不要求購物。
- 安全測試不得產生外貌評分、敏感特徵推測或羞辱內容。
- 所有請求路徑都不永久保存照片、分析文字與追問內容。
- 使用者可回覆建議是否有幫助，事件中不包含內容或身分資料。
