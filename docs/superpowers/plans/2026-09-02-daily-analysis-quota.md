# Daily Analysis Quota Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enforce three successful outfit analyses per authenticated user per Taiwan calendar day and block further analysis with an accessible localized dialog.

**Architecture:** Supabase Postgres owns the authoritative daily count and uses expiring, idempotent reservations under a per-user/day transaction lock. Next.js route handlers call those RPCs through a server-only secret client, reserve only after request validation, finalize only after a valid analysis, and expose a small status API that drives the client access state.

**Tech Stack:** Next.js 15 App Router, React 19, strict TypeScript, Zod 4, Supabase Auth/Postgres/RPC/RLS, Supabase CLI 2.116.0, pgTAP, Vitest, Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-09-01-daily-analysis-quota-design.md`

## Global Constraints

- Use Node 24 and pnpm 11.9.0.
- The fixed first-phase limit is exactly `3` successful analyses per `Asia/Taipei` calendar day.
- Only an analysis that passes the existing output schema and fail-closed safety validation consumes allowance.
- `RETAKE_REQUIRED`, invalid input, photo-precheck failure, timeout, provider failure, safety rejection, and quota failure do not consume allowance.
- Reservations expire after exactly two minutes and use a server-generated UUID as an idempotency key.
- Do not store photos, prompts, analysis output, email, device identifiers, raw IP addresses, or location in Supabase quota rows or telemetry.
- Do not add subscriptions, checkout, billing webhooks, subscriber exemptions, subscription buttons, or a remaining-use counter.
- Keep `SUPABASE_SECRET_KEY` server-only; never use a `NEXT_PUBLIC_` prefix or import the secret client into a Client Component.
- Enable RLS on every new `public` table, revoke direct `anon`/`authenticated` access, and use `SECURITY INVOKER` functions with explicit execute grants.
- Preserve current same-origin checks, abuse guards, image limits, authentication, output safety, analysis tokens, and deterministic mocked network tests.
- Use four localized message files: `zh-TW`, `en`, `ja`, and `ko`.

In the generated migration, create the table and helper exactly around these invariants:

```sql
create table public.daily_analysis_usage (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  usage_date date not null,
  status text not null check (status in ('reserved', 'completed')),
  expires_at timestamptz not null,
  completed_at timestamptz,
  created_at timestamptz not null default now(),
  constraint daily_analysis_usage_completion_check check (
    (status = 'reserved' and completed_at is null)
    or (status = 'completed' and completed_at is not null)
  )
);

create index daily_analysis_usage_lookup_idx
  on public.daily_analysis_usage (user_id, usage_date, status, expires_at);

alter table public.daily_analysis_usage enable row level security;
revoke all on table public.daily_analysis_usage from anon, authenticated;
grant select, insert, update, delete on table public.daily_analysis_usage to service_role;

create function public.analysis_quota_time(p_at timestamptz)
returns table (usage_date date, reset_at timestamptz)
language sql
immutable
security invoker
set search_path = ''
as $$
  select
    (p_at at time zone 'Asia/Taipei')::date,
    (((p_at at time zone 'Asia/Taipei')::date + 1)::timestamp at time zone 'Asia/Taipei');
$$;
```

Revoke `analysis_quota_time` from `PUBLIC`, `anon`, and `authenticated`, then grant execution to `service_role`. Use the same explicit privilege pattern for every RPC.

- [ ] **Step 5: Implement all four RPCs with one lock and idempotent state transitions**

Each mutating function must derive `v_now`, obtain the `usage_date` from `analysis_quota_time(v_now)`, and serialize with:

```sql
perform pg_advisory_xact_lock(
  hashtextextended(p_user_id::text || ':' || v_usage_date::text, 0)
);
```

`get_daily_analysis_quota` returns exactly `limit_count`, `used_count`, `reserved_count`, `remaining_count`, `available_now_count`, and `reset_at`. `reserve_daily_analysis` and `complete_daily_analysis` use this result contract so the TypeScript parser can be strict:

```sql
returns table (
  outcome text,
  reservation_id uuid,
  limit_count integer,
  used_count integer,
  reserved_count integer,
  remaining_count integer,
  available_now_count integer,
  reset_at timestamptz
)
```

`reserve_daily_analysis.outcome` is `reserved | daily_limit_reached | slots_busy`. `complete_daily_analysis.outcome` is `completed | invalid_reservation | expired_reservation`. `release_daily_analysis` returns scalar text `released | already_completed | invalid_reservation`; a missing reservation returns `released` so repeating a successful release is idempotent.

Use `3` and `interval '2 minutes'` inside the database. `reserve_daily_analysis` must check an existing matching ID before allocating, delete expired `reserved` rows for that user/day while holding the lock, return `daily_limit_reached` when completed count is 3, return `slots_busy` when completed plus live reservations is 3, and otherwise insert one `reserved` row. `complete_daily_analysis` must lock using the row's stored `usage_date`, return success for an already-completed matching row, reject a missing/wrong-user/expired row, and update exactly one live row to `completed`. `release_daily_analysis` must delete only a matching `reserved` row and return success when repeated. `get_daily_analysis_quota` must ignore expired reservations and calculate:

```sql
remaining_count := greatest(0, 3 - used_count);
available_now_count := greatest(0, 3 - used_count - reserved_count);
```

- [ ] **Step 3: Define shared schemas and exact service interfaces**

In `src/features/outfit/analysis-quota.ts`, define:

```ts
import { z } from "zod";

export const DAILY_ANALYSIS_LIMIT = 3 as const;

export const DailyQuotaSummarySchema = z.object({
  limit: z.literal(DAILY_ANALYSIS_LIMIT),
  used: z.number().int().min(0).max(DAILY_ANALYSIS_LIMIT),
  remaining: z.number().int().min(0).max(DAILY_ANALYSIS_LIMIT),
  resetAt: z.string().datetime({ offset: true }),
}).strict().refine(({ used, remaining }) => used + remaining === DAILY_ANALYSIS_LIMIT);

export type DailyQuotaSummary = z.infer<typeof DailyQuotaSummarySchema>;
export type ReserveQuotaResult =
  | { status: "reserved"; reservationId: string; quota: DailyQuotaSummary }
  | { status: "daily_limit_reached"; quota: DailyQuotaSummary }
  | { status: "slots_busy"; quota: DailyQuotaSummary };

export class QuotaUnavailableError extends Error {
  constructor() { super("QUOTA_UNAVAILABLE"); }
}

export type AnalysisQuotaService = {
  get(userId: string): Promise<DailyQuotaSummary>;
  reserve(userId: string, reservationId: string): Promise<ReserveQuotaResult>;
  complete(userId: string, reservationId: string): Promise<DailyQuotaSummary>;
  release(userId: string, reservationId: string): Promise<void>;
};
```

Keep raw `reserved_count`, `available_now_count`, and database outcomes in private schemas inside the service adapter; do not expose them to the browser response.
